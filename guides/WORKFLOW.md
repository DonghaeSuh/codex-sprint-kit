# 180분 작업 운영
## 0–20분: 이해와 첫 계획
1. README·제출 형식·기존 파일·실행 명령을 확인합니다.
2. 사용자/업무/대표 성공 사례/치명적 실패를 정리합니다.
3. 필수 요구사항에 R1, R2처럼 ID를 부여하고 확인 방법을 붙입니다.
4. 필요한 질문만 업무 담당자에게 묻고 답변의 출처를 기록합니다.
5. 첫 동작을 입력부터 결과까지 이어지는 최소 흐름으로 정합니다.

## 20–85분: 구현
먼저 핵심 흐름을 끝까지 실행합니다. 함수 수·코드량으로 진도를 측정하지 않습니다.
단일 구현 스트림을 유지하고 서버는 별도 터미널에서 실행합니다.
기능 하나가 동작하면 해당 acceptance 근거와 STATE를 갱신합니다.
아직 공개되지 않은 채점 비중을 임의로 숫자로 만들지 않습니다.

## 85–145분: 개선과 완성도
한 주기 15–25분: 실패 확인 2분 → 가설 2분 → 수정 8–12분 → 비교 3–5분 → 기록 2분.
기준 입력을 고정하고 주요 변경 하나만 실험합니다.
업무 정확도, 필수 기능, 재현성, 오류 처리, 사용자 이해도 순으로 우선합니다.
확률적 출력은 중요한 불확실 사례만 반복합니다. 전수 반복을 기본으로 하지 않습니다.

### 실험 요청
> R3이 입력 X에서 실패한다. 관련 코드를 읽고 가설 하나를 정해라.
> 15분 안에 최소 변경 후 같은 검사를 실행해라.
> 개선 전후 근거와 회귀를 보고하고 유지/복원/판정 불가를 기록해라.

### 디버깅 요청
> 이 명령과 입력으로 오류를 재현해라. 최초 실패 경계와 최근 변경을 확인해라.
> 환경 전체를 덤프하지 말고 필요한 근거만 수집해라.
> 원인을 설명할 수 있을 때 수정하고 원래 실패 및 인접 사례를 검증해라.

## 145–180분: 검증과 제출
새 기능을 줄이고 저장·실행·파일 형식·요구 충족을 확인합니다.
필수 UI는 사람이 직접 입력하며 확인합니다. 테스트 통과가 수동 UI 검증을 대체하지 않습니다.
사용자가 문제, 결정, 실제 결과, 남은 한계를 설명할 수 있어야 합니다.
최종 제출은 플랫폼 지침에 맞춰 사람이 수행합니다.

## 세션 운영
- 실제 제공된 CLI에서 /status, /model과 도움말을 확인합니다.
- 모델명은 제공 목록 그대로 사용하고 별도 API 인증을 추가하지 않습니다.
- 선택적 codex exec는 설치 버전의 도움말 확인 후 사용합니다.
- 동시에 구현자가 여러 명이면 공유 파일 충돌과 메모리 사용이 늘 수 있습니다.
- 기본은 구현자 1개, 필요하면 읽기 전용 검토 1개입니다.
- 프롬프트에는 목표·근거·범위·시간·수용 조건을 넣습니다.
- ADR은 큰 선택만 기록하고 작업별 상세 로그를 항상 문맥에 넣지 않습니다.

## 장애
MCP/추가 도구 설정에 3분이 넘으면 기본 도구로 돌아갑니다.
오류를 숨기거나 검사를 약화시키지 않습니다.
제한에 막힌 작업은 우회하지 말고 환경의 문의 절차를 사용합니다.
반복 오류의 시각·단계·오류 문구만 기록하고 키·문제 내용을 외부로 보내지 않습니다.
